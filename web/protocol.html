OSTP
Open Sonic Transport Protocol

RTPをベースにしたリアルタイムオーディオトランスポートプロトコル。
LAN内5ms以下の超低遅延からグローバルP2Pスワーム配信まで、
あらゆるスケールのオーディオ伝送を単一プロトコルで実現します。

設計の背景

なぜ WebRTC ではダメなのか

WebRTC は優れたプロトコルです。しかし「1対多のリアルタイムオーディオ配信」において、OSTPs が解決する問題に正面から向き合っていません。

比較項目 OSTP WebRTC AES67
接続モデル チャンネル名で即接続 SDP/ICE ネゴシエーション必須 LAN内マルチキャスト専用
1対多配信 ネイティブサポート SFU/MCU サーバーが別途必要 WAN不可
P2P スウォーム プロトコルレベルで定義 仕様外（アプリ層で実装要） なし
経済レイヤー CHARGE/SYNC コマンド内蔵 なし なし
実装複雑度 低（UDP + 24バイトヘッダ） 高（DTLS-SRTP, ICE, SDP…） 中（PTP同期が複雑）
モバイル対応 iOS / Android ネイティブ ブラウザのみ安定 対応なし
WebRTC の限界

1対多は設計外。SFUを構築すれば可能だが、それはWebRTCではなくSFUアーキテクチャ。P2Pスウォームを組み込むにはシグナリングプロトコル全体の再設計が必要。

AES67 の限界

放送・スタジオ向け。LAN内マルチキャストのみで、WANルーティング不可。モバイル・ブラウザは考慮外。PTP同期インフラが前提。

OSTP の立ち位置

RFCに準拠しつつ、「1人の送信者から世界規模の受信者へ」というユースケースに最適化。チャンネル名1つで繋がるシンプルさとスウォーム拡張を両立。

接続モード

4つの接続モード

ネットワーク環境に応じて最適なモードを自動選択。LANの超低遅延からグローバル配信まで、シームレスに切り替わります。

⚡

LAN モード

< 5ms

同一ネットワーク内のデバイス間で、mDNS/Bonjourによる自動ディスカバリー。マルチキャストUDPで直接パケット送信し、ルーティングオーバーヘッドなしの最低遅延を実現。ホームオーディオの複数スピーカー完全同期に最適。

🔗

P2P モード

2–4 devices, <50ms

リレーがYOUR_ADDRレスポンスでクライアントの外部IP:ポートを通知し、UDP ホールパンチングでNAT越えを実現。少人数のプライベートセッションやリモートDJモニタリングに最適。リレーサーバーを経由しないため帯域コストゼロ。

🌐

Relay モード

5+ devices, ~100ms

Fly.ioにデプロイされた地理分散リレーサーバー経由で配信。5台以上のデバイスやNAT越えが困難な環境で自動的に選択。リレーサーバーはパケットをフォワードするだけで、デコードや再エンコードは行いません。

⚖

Hybrid モード

Auto-select

ネットワーク状況をリアルタイムで計測し、最適なモードを自動選択。LANデバイスにはマルチキャスト、WANリスナーにはP2PまたはRelay。モード遷移はシームレスで、リスナーに途切れを感じさせません。

セキュリティ

セキュリティ

トランスポート層からアプリケーション層まで、多層的なセキュリティを実装。プロトコルレベルで安全性を担保します。

🔑

HMAC-SHA256

入金操作（CHARGEコマンド）にHMAC-SHA256署名を付与。改ざんされた入金リクエストはリレーが即座に拒否し、不正な残高操作を防止します。

🔐

DTLS-SRTP

音声データの暗号化にDTLS-SRTPをサポート（オプション機能）。リレー起動時に証明書を設定した場合のみ有効化されます。P2Pおよびリレー経路上の盗聴を防止し、鍵交換はDTLSハンドシェイクで自動的に行われます。

🔒

TLS (金融操作)

ウォレットAPI、決済処理、ロイヤリティ分配などの金融操作はすべてTLS 1.3で暗号化されたHTTPS経由で実行。UDPトランスポートには一切の金融データを載せません。

経済レイヤー

経済レイヤー

トランスポートと経済ロジックを明確に分離。プロトコルはオーディオ伝送に専念し、ビジネスロジックはアプリケーション層で処理します。

分散フィンガープリント検出

リスナー側分散フィンガープリント検出

送信者の負荷ゼロ。リスナーのデバイスが受信中の音声からフィンガープリントを生成し、リレーサーバーが合意アルゴリズムで楽曲を特定。リスナーが増えるほど精度が上がるP2P型の著作権検出システム。

🎵

1. フィンガープリント生成

30秒ごと / 64bit

リスナーのiPhone/ブラウザが受信中の音声を解析。5秒の音声から8周波数帯 x 32時間窓で64bitハッシュを生成。Accelerate (iOS) / Web Audio API (ブラウザ) で処理し、バッテリー消費はほぼゼロ。

📡

2. リレーへ送信

~200バイト

生成されたハッシュをリレーサーバーに送信。データ量はわずか約200バイトで通信負荷はほぼゼロ。音声データ自体は一切送信されないためプライバシーも保護。

🤝

3. 合意アルゴリズム

2人以上で確定

リレーが複数リスナーのレポートを集計。2人以上が同じハッシュを報告した場合に楽曲を確定。ハミング距離 8bit 以内で同一楽曲と判定。多数決により不正レポートを自動排除。

💰

4. マッチング & 自動分配

リアルタイム

確定したハッシュを楽曲データベースとマッチング。一致した楽曲の権利者に自動でロイヤリティを分配。権利者70%、DJキャッシュバック20%、プラットフォーム10%。

🔢

ハッシュ仕様

5秒の音声窓 → FFTで8周波数帯 (200Hz〜25.6kHz) を抽出 → 32時間窓でエネルギー比較 → 64bitハッシュを生成。レポート保持期間は60秒で自動クリーンアップ。

🔋

バッテリー影響ゼロ

音声は再生のために既にデコード済み。追加処理はFFTのみ。iOS Accelerateフレームワーク / Web Audio APIのAnalyserNodeで超低負荷で処理。

🛡

改ざん防止

複数リスナーの多数決で不正レポートを排除。中央集権的な監視ではなく、リスナーネットワーク全体で著作権を保護する分散型の仕組み。

Fanout-4 ツリー構造

各ノードは最大4つの子ノードにパケットを転送。ツリーの深さが増すごとに指数関数的にリスナー数がスケールします。16ノード (深さ2) で64リスナー、深さ3で256リスナーに到達可能。

📱
モバイル自動検出

セルラー回線（4G/5G）のリスナーは自動的にリーフノードとして配置されます。不安定なモバイル回線がリレーになることを防ぎ、下流リスナーへの連鎖的な接続断を回避します。

🛡
冗長親フェイルオーバー

各ノードはプライマリ親に加えてセカンダリ親への接続を維持。親ノードが離脱した場合、50ms以内にセカンダリ親へ自動切り替え。リスナーは途切れを感じることなく聴取を継続できます。

📊
リレーフォールバック

P2Pツリーの構築に失敗した場合や、NATタイプがSymmetricでピア接続が不可能な場合、自動的にリレーモードへフォールバック。接続性を常に保証します。
