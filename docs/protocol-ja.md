# OpenSonic Transport Protocol (OSTP) 仕様書

**バージョン**: 1.0
**ステータス**: ドラフト
**日付**: 2026-03-12

## 1. 概要

OSTPは、RTP (RFC 3550) をベースとしたリアルタイム音声トランスポートプロトコルである。以下の機能を提供する:

- **低遅延PCMストリーミング** — LAN (マルチキャスト) およびWAN (リレー) 対応
- **マルチデバイス同期再生** — ウォールクロックタイムスタンプによる精密同期
- **ハイブリッドP2P/サーバートポロジー** — 少人数はメッシュ自動構成、大規模はリレーへスケール
- **チャンネル所有権と権限管理** — オーナーがブロードキャスト権を制御
- **AES67相互運用** — プロフェッショナルオーディオネットワークとの接続

### 2.2 フィールド定義

| フィールド | バイト数 | 説明 |
|-------|-------|-------------|
| Version (V) | 2ビット | 常に `2` (RTP v2) |
| Padding (P) | 1ビット | `0` |
| Extension (X) | 1ビット | 常に `1` (OSTP拡張ヘッダあり) |
| CSRC Count (CC) | 4ビット | `0` |
| Marker (M) | 1ビット | `0` (予約) |
| Payload Type (PT) | 7ビット | §2.3 を参照 |
| Sequence Number | 2バイト | 32ビットシーケンスの下位16ビット |
| RTP Timestamp | 4バイト | 48kHzでのサンプルカウント |
| SSRC | 4バイト | 同期ソース識別子 |
| Profile | 2バイト | `0x4F53` ("OS") — OSTP拡張の識別子 |
| Extension Length | 2バイト | `2` (32ビットワード×2 = 8バイト) |
| Stream ID | 2バイト | 論理ストリーム識別子 |
| Sequence Extension | 2バイト | 32ビットシーケンスの上位16ビット |
| Media Timestamp | 4バイト | ウォールクロック・ナノ秒（エポックnsの下位32ビット） |
| CRC-32 | 4バイト | ペイロードのみに対するIEEE 802.3 |

### 2.3 ペイロードタイプ

| PT | フォーマット | サンプルサイズ | 説明 |
|----|--------|-------------|-------------|
| 96 | PCM S24 | 4バイト (int32, 24ビット範囲) | 主要オーディオフォーマット |
| 97 | Float32 | 4バイト (IEEE 754) | 高精度オーディオ |
| 98 | Opus | 可変長 | 圧縮オーディオ |
| 10 | AES67 L24 | 3バイト (24ビット ビッグエンディアン) | AES67互換 |
| 11 | AES67 L16 | 2バイト (16ビット ビッグエンディアン) | AES67互換 |
| 126 | NACK | 可変長 | 再送要求 (WiFi用) |
| 127 | FEC | 可変長 | 前方誤り訂正パリティ |

### 2.4 CRC-32アルゴリズム

IEEE 802.3多項式 `0xEDB88320`（反転）を使用し、ペイロードバイトのみを対象に計算する:

```c
uint32_t crc32(const uint8_t* data, size_t len) {
    uint32_t crc = 0xFFFFFFFF;
    for (size_t i = 0; i < len; i++) {
        crc ^= data[i];
        for (int j = 0; j < 8; j++)
            crc = (crc >> 1) ^ (0xEDB88320 & -(crc & 1));
    }
    return ~crc;
}
```

## 3. リレーシグナリングプロトコル

ポート **5100** 上のUDPテキストベースコマンド。すべてのコマンドは改行で終端する。

### 3.1 接続

```
→ JOIN:<group>:<password>:<device_name>\n
← OK:joined\n
← ROLE:<owner|dj|listener>\n
← META:<json>\n              (キャッシュがある場合)
← FILE:<filename>\n          (キャッシュがある場合)
← SYNC:<action>:<pos>:<ts>\n (キャッシュがある場合)
← PEER:<ip>:<port>\n         (既存メンバーごとに送信)

→ HELLO\n                    (5秒ごとのキープアライブ)

→ PING:<target_ip>:<target_port>:<timestamp_ms>\n
← (リレーがターゲットに転送): PING:<sender_ip>:<sender_port>:<timestamp_ms>\n
← (ターゲットが送信者に直接応答): PONG:<timestamp_ms>\n

→ ROUTE:<peer_ip>:<peer_port>:<p2p|relay>\n   (情報通知、リレーからの応答なし)
```

### 3.2 チャンネル管理

```
→ CHECK:<name>\n
← OK:available\n | OK:taken\n

→ CLAIM:<name>:<device>:<txn>\n
← OK:claimed\n | OK:renewed\n | ERR:taken\n | ERR:reserved_name\n

→ RELEASE:<name>:<device>\n
← OK:released\n
```

### 3.3 ロール管理

```
→ GRANT:<dj|listener>:<device_name>\n    (オーナーのみ)
← OK:granted\n
   → ターゲットが受信: ROLE:<dj|listener>\n

→ MEMBERS\n
← MEMBERS:{"group":"...","mode":"public|private","members":[{"device":"...","role":"...","addr":"..."}]}\n

→ MODE:<private|public>\n    (オーナー、または無料チャンネルのDJ)
← MODE:<private|public>\n    (全メンバーにブロードキャスト)
```

チャンネルモード:

| モード | リレー転送 | 検索結果への表示 | 著作権検出 | 用途 |
|------|-----------------|-------------------|-------------------|----------|
| `public` | あり (デフォルト) | あり | あり | 公開DJセット、ラジオ局 |
| `private` | フォールバック時のみ | なし | なし | 家庭内オーディオ、友人間、練習用 |

- オーナー/DJはいつでも `MODE:` コマンドでモードを切り替え可能
- モード変更時、全メンバーに新しい `MODE:` 通知が送信される
- プライベートモードではP2Pホールパンチ用の `PEER:` アドレス交換が行われる
- LANマルチキャストおよびP2P直接接続はリレーを経由しないため、モード設定に関係なく著作権検出は適用されない

### 3.4 ブロードキャスト制御 (DJまたはオーナーロールが必要)

```
→ META:<json>\n           (グループにメタデータをブロードキャスト)
→ FILE:<filename>\n       (ダウンロード用ファイルを通知)
→ SYNC:play:<pos_ms>:<wall_clock_ms>\n
→ SYNC:pause:<pos_ms>:<wall_clock_ms>\n
→ SYNC:seek:<pos_ms>:<wall_clock_ms>\n
→ <OSTP audio packet>    (バイナリ、0x80プレフィックス)
```

### 3.5 再生機能

```
→ READY:<filename>\n      (受信側: ファイルダウンロード完了)
→ REPLAY:<seconds>\n      (タイムシフト要求、最大300秒)
← OK:replay:<count>\n
→ RECORD:<group>\n        (サーバーサイド録音開始)
← OK:recording\n
→ RECORD_STOP:<group>\n
← OK:record_stopped\n
```

### 3.6 エラーレスポンス

| エラー | 意味 |
|-------|---------|
| `ERR:empty_group` | JOINにグループ名がない |
| `ERR:channel_reserved` | チャンネルは他のデバイスが所有している |
| `ERR:wrong_password` | グループパスワードが不正 |
| `ERR:group_full` | メンバー数上限に到達 (デフォルト: 16) |
| `ERR:max_groups` | グループ数上限に到達 (デフォルト: 100) |
| `ERR:no_permission` | 操作に必要なロールが不足 |
| `ERR:not_owner` | GRANTにはオーナーロールが必要 |
| `ERR:not_in_group` | 送信者がどのグループにも属していない |
| `ERR:member_not_found` | 対象デバイスがグループに存在しない |
| `ERR:invalid_format` | コマンドの書式が不正 |
| `ERR:invalid_name` | チャンネル名のバリデーションに失敗 |
| `ERR:invalid_role` | 不明なロール文字列 |
| `ERR:taken` | チャンネルは他のデバイスが取得済み |
| `ERR:reserved_name` | ビルトインの予約名 |

## 4. チャンネル所有権モデル

### 4.1 チャンネル種別

| 種別 | フォーマット | 費用 | 権限 |
|------|--------|------|-------------|
| ランダム | 6文字の16進数 (例: `a3f9b2`) | 無料 | 全員 = DJ |
| ビルトイン | `soluna`, `default`, `test`, `admin`, `music`, `jazz`, `tokyo` 他 | 無料 | 全員 = DJ |
| カスタム | 3〜20文字、英数字 + ハイフン | 年額購入 | オーナーが制御 |

### 4.2 ロール

| ロール | 音声送信 | META/FILE/SYNC | GRANT/REVOKE | 優先度 |
|------|----------|----------------|--------------|----------|
| Listener | — | — | — | 0 |
| DJ | ✓ | ✓ | — | 1 |
| Owner | ✓ | ✓ | ✓ | 2 |

### 4.3 ロール割り当てルール

- **無料/ランダムチャンネル**: 全メンバーがDJとして参加
- **所有チャンネル**: オーナーデバイスにOwner、最初の参加者にDJ、それ以外にListenerが割り当てられる
- オーナーは `GRANT:` コマンドで昇格/降格が可能
- ロールはセッション中持続する（再参加時に再評価）

### 4.4 チャンネル名ルール

- 文字数: 3〜20文字
- 使用可能文字: `a-z`, `A-Z`, `0-9`, `-`
- 全桁16進数の名前はランダム生成用に予約
- プレミアム予約名: 付録A参照
- 有効期限: CLAIM/更新から365日

## 5. 同期再生

### 5.1 メディアタイムスタンプ

`media_timestamp`フィールドは、音声のキャプチャ/エンコード時点における送信者のウォールクロック時刻のナノ秒値の下位32ビットを格納する。

```
media_timestamp = (uint32_t)(nanoseconds_since_epoch & 0xFFFFFFFF)
```

### 5.2 受信側同期アルゴリズム

各受信側は、メディアタイムスタンプから最適なバッファ深度を計算する:

```
network_delay_ns = (now_ns_32bit - media_timestamp)  // ラッピング減算
network_delay_ms = network_delay_ns / 1e6
ideal_buffer_ms  = target_delay_ms - network_delay_ms
ideal_buffer_ms  = clamp(ideal_buffer_ms, 10.0, 500.0)

// EMAで平滑化 (alpha = 0.01)
target_fill += 0.01 * (ideal_frames - target_fill)
```

### 5.3 統一再生パラメータ

以下のパラメータは、すべての受信側実装で同一でなければならない (MUST):

| パラメータ | 値 | 説明 |
|-----------|-------|-------------|
| サンプルレート | 48000 Hz | 固定 |
| 目標フィル | 2880フレーム (60 ms) | デフォルトのバッファ目標 |
| リングバッファ | 192000フレーム (4秒) | 容量 (2の累乗) |
| ドリフトトリガー | 目標 × 3 | 破棄開始の閾値 |
| ドリフト速度 | frame_count / 80 + 1 | コールバックごとの破棄フレーム数 |
| ドリフトクロスフェード | 48フレーム | 破棄後の平滑化 |
| フェードイン | 0.002 | 音量ランプアップ係数 |
| フェードアウト | 0.004 | 音量ランプダウン係数 |
| サンプルスケール | 8388608.0 (2²³) | S24 ↔ float変換 |

### 5.4 ファイル同期 (ハイブリッドDJモード)

DJモードは、即時PCMストリーミングとファイルベースの同期を組み合わせる:

```
1. DJが FILE:<name> を送信        → 受信側がダウンロード開始
2. DJがOSTOでPCMをストリーミング   → 受信側は即座に再生
3. 3秒後: DJが SYNC:play:<pos_ms>:<wall_ms> を送信
   → ファイル同期の受信側はローカルファイルに切り替え（完全同期）
   → PCM受信側はストリーミングを継続（十分な同期精度）
```

## 8. WiFi信頼性

### 8.1 FEC (前方誤り訂正)

```
モード: XORパリティ (デフォルト) または Reed-Solomon
グループ: 5データパケット + 1パリティ (設定可能)
PT: パリティパケットは 127
復元: 1グループあたり1パケットロスの復元 (XOR)、複数ロスの復元 (RS)
```

### 8.2 NACK (否定応答)

```
PT: 126
目的: 特定のシーケンス番号の再送を要求
フォーマット: PT=126のRTPヘッダ、ペイロード = 欠落シーケンス番号のリスト
```

## 9. 接続選択 (P2P/リレー自動選択)

### 9.1 アルゴリズム

クライアントがグループに参加すると、既存メンバーごとに `PEER:<ip>:<port>` を受信する。その後、P2Pとリレーを競争させる:

```
1. リレー経由でPINGを送信（リレーがターゲットに転送）
2. 同時にピアのIP:portへ直接UDPを送信
3. ピアが両方の経路でPONGを返信
4. クライアントが各経路のRTTを計測
5. RTTの低い経路を採用
6. 2秒以内にP2P PONGが届かなければリレーにフォールバック
```

### 9.2 プロトコルコマンド

```
→ PING:<target_addr>:<timestamp_ms>\n
  リレーがターゲットに転送: PING:<sender_addr>:<timestamp_ms>\n
← PONG:<timestamp_ms>\n  (ターゲットが送信者に直接応答)

→ ROUTE:<peer_addr>:p2p\n     (情報通知: P2P直接接続を使用)
→ ROUTE:<peer_addr>:relay\n   (情報通知: リレーを使用)
```

### 9.3 重複排除

切り替え中に両方の経路からオーディオが到着する可能性がある。受信側は直近64個のシーケンス番号を循環バッファで追跡し、重複を破棄する。

### 9.4 キープアライブ

- P2P経路: 10秒ごとに直接PINGを送信
- 3回連続でPONGが返らない場合、リレーにフォールバック
- リレー経路は常にフォールバックとして機能

|------|-----------|--------|-------------|
| `lyric` | DJ/Owner | あり (`last_text`) | タイミング付きカラオケ歌詞 |
| `chat` | 全ロール | なし | ユーザーチャットメッセージ |
| `info` | DJ/Owner | なし | システム情報/アナウンス |

### 10.3 動作

- `lyric` タイプ: `group.last_text` として保存され、新規参加者に送信される
- `chat` タイプ: グループに転送されるが、キャッシュされない
- `ts` フィールド: 受信側がオーディオと同期した正確なウォールクロック時刻にテキストを表示できる
- `duration` フィールド: テキストの表示時間 (0 = 次のTEXTまで持続)

## 11. DJ + マイクミキシング

### 11.1 概要

DJは音楽の上にマイク音声をミキシングして送信できる。これは**送信側で**処理される — 1本のミックス済みOSTPストリームが送信されるため、受信側の変更は不要。

### 11.2 ミックスシグナル

```
→ MIX:on\n      (DJ+マイクのミックスオーディオを送信中)
→ MIX:off\n     (単一ソースのみを送信中)
← MIX:<device>:on\n   (リレーがグループに通知)
← MIX:<device>:off\n  (リレーがグループに通知)
```

### 11.3 ミキシングアルゴリズム (送信側)

```
output = music_pcm * music_gain + mic_pcm * mic_gain
output = clamp(output, -1.0, 1.0)

デフォルトゲイン:
  music_gain = 0.7  (マイクがアクティブ時に自動ダッキング)
  mic_gain   = 1.0
```

### 11.4 MEMBERSでのミックス状態

```json
{
  "group": "channel",
  "members": [
    {"device": "dj-mac", "role": "dj", "mixing": true, "addr": "1.2.3.4:5678"}
  ]
}
```

## 12. リレーカスケード (グローバルスケール)

OSTPは、マルチティアのリレーカスケードによるグローバル規模のオーディオ配信をサポートする。
1つのDJストリームで数十億の同時リスナーに到達できる。

### 12.1 トポロジー

```
                        DJ (source)
                           │
                    ┌──────┴──────┐
                    │   ORIGIN    │  1 instance
                    │   (tier 1)  │  Receives DJ audio
                    └──┬───┬───┬──┘
                       │   │   │
              ┌────────┘   │   └────────┐
              ▼            ▼            ▼
         ┌────────┐  ┌────────┐  ┌────────┐
         │REGION 1│  │REGION 2│  │REGION N│  ~20 instances
         │(tier 2)│  │(tier 2)│  │(tier 2)│  One per geographic region
         └─┬──┬──┬┘  └────────┘  └────────┘
           │  │  │
     ┌─────┘  │  └─────┐
     ▼        ▼        ▼
  ┌──────┐┌──────┐┌──────┐
  │EDGE 1││EDGE 2││EDGE M│  ~10K instances total
  │(tier3)││(tier3)││(tier3)│  ~500 per region
  └──┬───┘└──────┘└──────┘
     │
     ▼
  Listeners (up to 300K per edge)
```

### 12.2 ティアの役割

| ティア | 役割 | ファンアウト | 一般的なインスタンス数 |
|------|------|---------|---------------|
| Origin (1) | DJオーディオを受信し、リージョンに配信 | 1 → 20 | 1 |
| Region (2) | 地理的ハブ、ローカルエッジに配信 | 1 → 500 | 約20 |
| Edge (3) | ラストマイル、リスナーに配信 | 1 → 300K | 約10K |
| Standalone | 単一リレー（後方互換、カスケードなし） | 1 → N | — |

### 12.3 カスケードプロトコル

下流リレーは、ポート5100のテキストコマンドを使用して上流のグループにサブスクライブする。

#### サブスクライブ

```
→ CASCADE_JOIN:<group>:<peer_id>:<secret>\n
← OK:cascade_joined\n
```

ローカルリスナーが上流サブスクリプションを必要とするグループに参加した際に、下流リレーがこれを送信する。`peer_id` は一意のリレー識別子（ランダム16進数16文字）。`secret` はカスケード認証用の共有トークン。

#### キープアライブ

```
→ CASCADE_HELLO:<peer_id>\n
```

5秒ごとに送信。上流は15秒間ハートビートがない下流ピアを除去する。

#### アンサブスクライブ

```
→ CASCADE_LEAVE:<group>:<peer_id>\n
← OK:cascade_left\n
```

#### 統計レポート

```
→ CASCADE_STATS:<peer_id>:{"listeners":<N>,"groups":["<g1>","<g2>"],"bw_mbps":<BW>}\n
```

30秒ごとに送信。上流がモニタリングおよび負荷分散のために集計する。

### 12.4 オーディオ転送

オーディオパケットは**下流方向のみ**に流れる — origin → region → edge → リスナー。

- 上流リレーは、サブスクライブ済みの各下流リレーにUDPで生のOSTPパケット（§2と同じフォーマット）を転送する。
- 下流リレーはこれらのパケットを受信し、自身のローカルメンバーおよびさらに下流へ転送する。
- **フレーミングやカプセル化は不要** — 下流リレーはCASCADE_JOIN時に登録された `sockaddr_in` で識別される。

DJオーディオはオリジンに向けて**上流**に流れる:
- DJがエッジまたはリージョンリレーに接続した場合、リレーはオーディオパケットを親に上流転送する。
- オリジンが受信し、カスケードを通じて下流に配信する。
- 代替案: DJをオリジンに直接接続させ、最小遅延を実現する。

### 12.5 メタデータ伝播

DJからの非オーディオコマンド (META, FILE, SYNC, TEXT, MIX, GRANT) はカスケードを通じて転送される:

1. DJがオリジンにコマンドを送信
2. オリジンがサブスクライブ済みの全リージョンリレーに転送
3. リージョンリレーがサブスクライブ済みの全エッジリレーに転送
4. エッジリレーがローカルリスナーに転送

各リレーは、スタンドアロンモードと同様に、新規参加者向けにMETA/FILE/SYNC/TEXTの最新値をキャッシュする。

### 12.6 キャパシティプランニング

Opus圧縮 128 kbps (リスナーあたり16 KB/s) の場合:

| 規模 | Origin帯域 | リージョン数 | エッジ数 | エッジ帯域 (各) |
|-------|-----------|---------|-------|-----------------|
| 10K | 320 KB/s | 1 | 10 | 16 MB/s |
| 100K | 320 KB/s | 5 | 100 | 16 MB/s |
| 1M | 320 KB/s | 20 | 1K | 16 MB/s |
| 100M | 3.2 MB/s | 20 | 10K | 160 MB/s |
| 1B | 32 MB/s | 20 | 100K | 160 MB/s |
| 3B | 32 MB/s | 20 | 300K | 160 MB/s |

Origin帯域は常に軽微（グループあたり リージョン数 × 16 KB/s）。
エッジ帯域はエッジあたりのリスナー数に比例してスケールする。160 MB/s（約1.3 Gbps）の場合、一般的な10GbEサーバーで300K以上のリスナーを処理できる。

### 12.7 sendmmsg() 最適化

Linuxでは、エッジが `sendmmsg(2)` を使用して最大1024回の `sendto()` を1回のシステムコールにバッチ処理し、カーネルオーバーヘッドを約10分の1に削減する。ワーカースレッド（デフォルト4）と組み合わせることで、単一エッジで10 Gbps NICを飽和させることが可能。

```c
// 疑似コード — 全iovecが同じパケットバッファを共有
struct mmsghdr msgs[1024];
for (int i = 0; i < batch_size; i++) {
    msgs[i].msg_hdr.msg_name = &destinations[i];
    msgs[i].msg_hdr.msg_iov = &iov;  // shared packet
    msgs[i].msg_hdr.msg_iovlen = 1;
}
sendmmsg(sock, msgs, batch_size, 0);
```

### 12.8 デプロイモード

```
# スタンドアロン（既存動作、変更なし）
soluna-relay --port 5100

# Origin
soluna-relay --origin --cascade-secret <SECRET> --port 5100

# Region（オリジンに接続）
soluna-relay --region <origin_ip:5100> --cascade-secret <SECRET> --port 5100

# Edge（リージョンに接続）
soluna-relay --edge <region_ip:5100> --cascade-secret <SECRET> --port 5100 --workers 8
```

### 12.9 障害処理

| 障害 | 動作 |
|---------|----------|
| エッジの停止 | リスナーが切断。DNS/エニーキャスト経由で別のエッジに再接続 |
| リージョンの停止 | エッジが上流の停滞を検出（5秒間オーディオなし）。別のリージョンに再接続 |
| オリジンの停止 | 全オーディオが停止。DJがバックアップオリジンに再接続（手動フェイルオーバー） |
| ネットワーク分断 | 各パーティションが独立動作。復旧時にシーケンス番号による短時間の重複排除が発生 |

### 12.10 地理的ルーティング

リスナーは以下の手段で最寄りのエッジリレーにルーティングされる:

1. **エニーキャストDNS** — 同一ホスト名が最寄りのエッジに解決される
2. **Fly.ioリージョン** — `nrt`, `iad`, `lhr`, `sin`, `gru` 等にエッジをデプロイ
3. **リダイレクト** — リレーが `REDIRECT:<closer_relay_host:port>\n` を返し、負荷の少ない、または近いエッジにリスナーを誘導

### 12.11 自動ティア選択

小規模チャンネル（リスナー100未満）では、カスケードは不要なオーバーヘッドとなる。システムは以下のように自動選択する:

| リスナー数 | トポロジー |
|-----------|----------|
| 2-4 | P2P直接 (§9) |
| 5-100 | 単一リレー (スタンドアロン) |
| 100-100K | Origin + エッジ (2ティア) |
| 100K+ | Origin + リージョン + エッジ (3ティア) |

リスナー数が閾値を超えると、スタンドアロンからカスケードへのプロモーションが行われる。既存リレーからオリジンが選出され、エッジが動的にスピンアップされる。

## 13. P2Pスワーム配信

すべてのリスナーがマイクロリレーとして機能し、他のリスナーにオーディオを転送できる。これにより、サーバー帯域コストがほぼゼロで数十億のリスナーにスケールするピアツーピアツリーが構築される。

### 13.1 動機

| アプローチ | 10億リスナーに必要なサーバー帯域 | コスト |
|----------|-----------------------------------|------|
| サーバーリレー | 10億 × 16 KB/s = 16 PB/s | 月額 数十億ドル |
| カスケード (§12) | 約10万エッジ × 16 KB/s = 1.6 GB/s | 月額 数百万ドル |
| P2Pスワーム | ファンアウト × 16 KB/s = 64 KB/s | 月額 約$0 |

オーディオのビットレートが小さい（Opusで128 kbps）ため、P2Pが実用的 — モバイルデバイスでも4ピアへのリレーが可能。

### 13.2 トポロジー

```
           DJ (source)
            │
      ┌─────┼─────┐
      ▼     ▼     ▼
      A     B     C     ← depth 1 (ルートノード、リレーから受信)
     /|\   /|\   /|\
    D E F G H I J K L   ← depth 2 (A/B/Cから受信し、子ノードへ転送)
   /|\ ...              ← depth 3 ...
```

ファンアウト4の場合:
- 深度1: 4ノード
- 深度5: 1,024ノード
- 深度10: 約100万ノード
- 深度16: 約42億ノード

深度16での最大遅延: 16 × 20ms = 320ms（オーディオストリーミングとして許容範囲）。

### 13.3 アクティベーション

グループのメンバー数が閾値（デフォルト: 50）を超えると、リレーサーバーが自動的にP2Pスワームを有効化する。閾値以下では通常のリレー転送が使用される。

| グループサイズ | モード |
|------------|------|
| 2-4 | P2P直接 (§9) |
| 5-50 | リレー転送 |
| 50+ | P2Pスワーム |

### 13.4 プロトコルコマンド

#### クライアント → リレー

```
→ SWARM_READY\n
    クライアントが他のピアにオーディオを中継可能であることを示す。
    JOIN後に送信。対称NATの背後にいる、または
    バッテリーセーバーモードのクライアントはこれを送信すべきではない。

→ SWARM_UNABLE\n
    クライアントが中継不可能（対称NAT、モバイルデータセーバー、
    低バッテリー等）。常にリーフノードとなる。

→ SWARM_ACK:<parent_ip>:<parent_port>\n
    割り当てられた親ピアからのオーディオ受信に成功したことを確認。

→ SWARM_LOST:<parent_ip>:<parent_port>\n
    親からのオーディオが途絶（タイムアウト、切断）。
    リレーが一時的に直接オーディオを転送し、
    2秒以内に新しい親を探す。
```

#### リレー → クライアント

```
← SWARM_ASSIGN:<parent_ip>:<parent_port>:<child1_ip>:<child1_port>[:<childN_ip>:<childN_port>]\n
    完全な割り当て: <parent>からオーディオを受信し、リストされた子ノードに転送。
    親が0.0.0.0:0の場合、リレーから直接受信（ルートノード）。

← SWARM_ADD_CHILD:<child_ip>:<child_port>\n
    新しい子ノードを追加してオーディオを転送。

← SWARM_REMOVE_CHILD:<child_ip>:<child_port>\n
    この子ノードへの転送を停止（離脱または再割り当て）。

← SWARM_PROMOTE:<new_parent_ip>:<new_parent_port>\n
    親が変更された。新しい親からオーディオの受信を開始。
    旧親の切断またはリバランス時に送信される。
```

### 13.5 ツリー構築アルゴリズム

リレーはグループごとに幅優先ツリーを維持する:

1. **ルート選択**: DJ/Ownerノードが常にルート（深度0）。リレーからオーディオを受信し、子ノードに転送する。
2. **BFS割り当て**: 新規メンバーは、`fan_out`（4）未満の子を持つ最も浅いリレー可能ノードの子として配置される。
3. **リーフ専用ノード**: `SWARM_UNABLE` を送信したメンバーは常にリーフとして配置される（子ノードは割り当てられない）。
4. **増分更新**: 個々の参加/離脱ではツリー全体を再構築せず、影響を受けるブランチのみを修正する。

### 13.6 障害復旧

| イベント | 復旧方法 | 所要時間 |
|-------|----------|------|
| リーフの切断 | SWARM_REMOVE_CHILDで親に通知 | 即時 |
| 中間ノードの切断 | 孤立した子ノードにSWARM_PROMOTEを送信し、兄弟ノードに再配置 | 2秒以内 |
| ルートの切断 | 次のリレー可能メンバーをルートに昇格。移行中はリレーが直接オーディオを送信 | 2秒以内 |
| クライアントがSWARM_LOSTを送信 | リレーがフォールバックとして直接送信 + 新しい親を探索 | 2秒以内 |

復旧中（新しい親が割り当てられるまで）、リレーは孤立ノードに一時的に直接オーディオを転送し、1パケット間隔（10ms）を超えるオーディオの途切れを防ぐ。

### 13.7 クライアント実装

スワームモードの各クライアントは以下を行う:

1. 割り当てられた親（ルートの場合はリレー）から1本のOSTPオーディオストリームを**受信**
2. オーディオをローカルで**再生**
3. 同じ生のOSTPパケットをUDP `sendto()` で各子ノードに**転送**
4. 親の**ヘルスを監視** — 500msオーディオが届かなければ、リレーに `SWARM_LOST` を送信

転送は単純なmemcpyであり、デコード/再エンコードは不要。クライアントのCPU負荷は無視できるレベル。

```
receive_packet(parent) → play_audio(packet) → for each child: sendto(child, packet)
```

### 13.8 NAT越え

P2Pスワームではピア間のUDP送信が必要。NAT越えのアプローチ:

1. **リレー仲介のホールパンチ**: 親子割り当て時にリレーが双方のアドレスを送信。両ピアがNATを通して互いに初期パケットを送信。
2. **STUNフォールバック**: 1秒以内にホールパンチが失敗した場合、クライアントは `SWARM_UNABLE` を送信しリーフ専用となる。
3. **リレーフォールバック**: どのP2Pピアからも受信できないクライアントには、リレーが直接転送する（このクライアントは負荷を増やすが、他のピアが補償する）。

### 13.9 ハイブリッド: カスケード + スワーム

最大スケールを実現するには、カスケード（§12）とスワームを組み合わせる:

```
DJ → Origin → Region → Edge → [リスナーのP2Pスワーム]
```

各エッジリレーがローカルスワームを調整する。これにより:
- エッジ帯域: 全リスナーではなくルートノード（グループあたり4）のみ
- 10Kエッジ × 4ルートノード = 30億リスナーに対して40Kのサーバーサイド接続

### 13.10 帯域バジェット

| 役割 | 必要なアップロード帯域 | 一般的なデバイス |
|------|--------------|----------------|
| リーフ (受信のみ) | 0 | 任意のデバイス |
| リレーノード (ファンアウト4) | 4 × 128 kbps = 512 kbps | WiFiスマートフォン、一般的なブロードバンド |
| ルートノード (ファンアウト4) | 512 kbps | 良好なブロードバンド |

512 kbpsのアップロードは、事実上あらゆるインターネット接続（4G、WiFi、DSL）で利用可能。
従量制接続やバッテリー残量の少ないクライアントはSWARM_UNABLEでオプトアウトできる。

## 14. P2Pファイル配信

DJが音楽ファイルを再生する際、ファイル自体をP2Pでリスナーに配信し、リアルタイムストリーミングを完全に排除できる。リスナーはローカルコピーから再生し、SYNCコマンド（§5）で同期する。

### 14.1 この仕組みの重要性

| シナリオ | リスナーあたりの帯域 | 100万リスナーの場合 |
|----------|----------------------|--------------|
| リアルタイムストリーミング (Opus 128kbps) | 常時16 KB/s | 16 TB/s |
| P2Pスワームストリーミング (§13) | サーバー約0、ピアアップロード64 KB/s | サーバー約0 |
| P2Pファイル配信 + ローカル再生 | 1回のダウンロードのみ、以後0 | 合計約0 |

一般的な4分の楽曲（Opusで5 MB）の場合、P2Pファイル配信は数秒で完了する。その後、SYNC:playが同期ローカル再生をトリガーし、**継続的な帯域消費はゼロ**となる。

リアルタイムストリーミングが必要なのは以下の場合のみ:
- ライブマイクトーク（断続的、通常DJセッションの10%未満）
- エンコード済みファイルが存在しないコンテンツ

### 14.2 配信方法

#### 方法A: ファイルURL（最速、推奨）

```
→ FILE_URL:<url>:<sha256>:<size_bytes>\n
← (リレーが全メンバーにブロードキャスト)
← FILE_URL:<url>:<sha256>:<size_bytes>\n
```

DJがダイレクトダウンロードURL（CDN、クラウドストレージ、事前共有）を提供する。各リスナーが独立してダウンロードする。既存インフラでホストされた既知の楽曲に対して即座に機能する。

#### 方法B: P2Pチャンク配信（外部サーバー不要）

```
→ FILE_OFFER:<filename>:<size_bytes>:<sha256>:<num_chunks>\n
← FILE_MANIFEST:<filename>:<size_bytes>:<sha256>:<num_chunks>\n  (全員へ)
```

ファイルは64 KBのチャンクに分割される。DJが最初のチャンクを第一波のピアに配信し、そのピアが他のピアに再配信する（BitTorrent方式の指数関数的配信）。

### 14.3 P2Pチャンクプロトコル

#### チャンクサイズ

固定 **64 KB** (65,536バイト)。5 MBのファイル = 80チャンク。

#### チャンク追跡

```
→ FILE_HAVE:<sha256>:<bitfield_hex>\n
    利用可能なチャンクの16進エンコードされたビットフィールド。
    例: "ff0f" = チャンク0-11が利用可能、12-15が欠落。

→ FILE_COMPLETE:<sha256>\n
    クライアントが全チャンクを保持。完全なシーダーとなる。
```

#### ピアディスカバリ

```
← FILE_PEERS:<sha256>:<chunk_index>:<peer1_ip>:<peer1_port>[:<peer2_ip>:<peer2_port>...]\n
    リレーがクライアントに、特定チャンクを保持するピアを通知。
    クライアントはリストされた任意のピアからリクエスト可能。
```

#### ピアツーピアのチャンク交換

```
→ CHUNK_REQ:<sha256>:<chunk_index>\n    (ピアへ)
← CHUNK_DATA:<sha256>:<chunk_index>:<data_base64>\n    (ピアから)
```

チャンクは安全なUDP転送のためbase64エンコードされる。64 KB → 88 KBにエンコード。

### 14.4 配信戦略

リレーが効率的な「レアレストファースト」配信を調整する:

1. **第一波**: DJが異なるピアに異なるチャンクを送信（ストライプ配信）
   - ピアAがチャンク 0, 4, 8, ... を取得
   - ピアBがチャンク 1, 5, 9, ... を取得
   - ピアCがチャンク 2, 6, 10, ... を取得
   - ピアDがチャンク 3, 7, 11, ... を取得

2. **クロスシーディング**: 第一波のピアが互いにチャンクを交換
   - 約1秒後、4ピア全てが完全なファイルを保持

3. **指数関数的ファンアウト**: 各完全シーダーが4つの新しいピアにシード
   - 4 → 16 → 64 → 256 → 1,024 → ...
   - 100万ピアまで約10秒
   - 10億ピアまで約15秒

4. **URL加速**: FILE_URLも提供されている場合、ピアはP2Pと並行してHTTP経由で欠落チャンクをダウンロード。速い方を採用。

### 14.5 再生フロー

```
1. DJ: FILE_OFFER (またはFILE_URL)     → P2P配信開始
2. DJ: リアルタイムオーディオをストリーム  → リスナーが即座に聴取
3. バックグラウンド: ファイルがP2Pで配信  → 完全配布まで約5-15秒
4. DJ: SYNC:play:<position>:<ts>        → リスナーがローカルファイルに切り替え
5. リアルタイムストリーム停止             → 帯域消費がゼロに
6. DJがマイクで話す                      → 短時間のリアルタイムストリームバースト
7. DJ: 次の曲のFILE_OFFER               → サイクルを繰り返し
```

ステップ2-3の間、リスナーはリアルタイムストリーミングで楽曲を聴く。ファイル配信完了後（ステップ4）、シームレスにローカル再生に切り替わる。このハイブリッドアプローチにより、オーディオの途切れをゼロにできる。

### 14.6 完了ブロードキャスト

ファイルの全チャンクがリレー上で利用可能になった場合（DJのシーディング完了、または十分なピアがシーディング中）、リレーは以下をブロードキャストする:

```
← FILE_READY:<sha256>\n
```

全メンバーに対して、ファイルがP2Pピアまたはリレー経由で完全に取得可能であることを通知する。`FILE_COMPLETE` 済みのクライアントはこれを無視する。

### 14.8 ファイル検証

- **SHA-256ハッシュ**がFILE_OFFER/FILE_URLで提供され、整合性を保証
- 各チャンクは部分ハッシュで検証可能（Merkleツリーはオプション）
- 破損したチャンクは別のピアから再リクエスト

### 14.9 ストレージ管理

クライアントはダウンロード済みファイルをLRU方式でキャッシュする:
- デフォルトキャッシュ: 500 MB（設定可能）
- ファイルはSHA-256で識別（重複排除）
- 前回セッションのキャッシュが残っている場合、即座にFILE_COMPLETEを送信

### 14.10 総合的な帯域削減

2時間のDJセット（30曲、合計150 MB）の場合:

| 方法 | DJアップロード | サーバー帯域 | リスナーダウンロード |
|--------|-----------|-----------------|-------------------|
| リアルタイムストリーミング | 150 MB (ストリーム) | 150 MB × N | 150 MB (ストリーム) |
| P2Pファイル + 同期 | 150 MB (チャンク) | 約0 | 150 MB (P2P) |
| FILE_URL + 同期 | 約0 (URLのみ) | 約0 | 150 MB (CDNから) |

FILE_URLの場合: **DJのアップロードなし、サーバー転送なし、リスナーはCDNからダウンロード**。
P2Pチャンクの場合: **サーバー転送なし**、ピアツーピアトラフィックのみ。

リアルタイムストリーミングが必要なのはライブマイクトークのみ（2時間セットのうち約5〜10分）。

## 15. 著作権検出とロイヤリティ追跡

OSTPには著作権検出とロイヤリティ追跡が組み込まれており、楽曲の再生時に権利者に対する適切な報酬を保証する。システムは**オーディオ性能への影響ゼロ**で設計されている — 検出は非同期で実行される。

### 15.1 設計原則

1. **オーディオ品質最優先** — フィンガープリンティングがオーディオパイプラインをブロックしたり品質を低下させたりしない
2. **リレーのみ** — 検出はリレーサーバー上でのみ実行される。LANマルチキャストおよびP2P直接接続は監視されない。自宅では自由に使える。
3. **透明性** — DJとリスナーは再生中の楽曲と権利者を確認できる
4. **公正な報酬** — ロイヤリティは再生回数、リスナー数、再生時間ごとに追跡
5. **オープンデータベース** — 複数のフィンガープリントバックエンド対応（ACRCloud、AudibleMagic、Chromaprint/AcoustID、セルフホスト）

**適用範囲:**

| 接続モード | 著作権検出 | 理由 |
|----------------|-------------------|--------|
| LANマルチキャスト (§1.1) | なし | オーディオがリレーを通過しない |
| P2P直接 (§9) | なし | オーディオがリレーを通過しない |
| リレー (§3) | あり | オーディオがリレーサーバーを通過する |
| カスケード (§12) | あり (オリジンのみ) | オリジンリレーがオーディオを1回検査 |
| P2Pスワーム (§13) | あり (ファンアウト前) | リレーがルートノードへの配信前にDJからのオーディオを確認 |

### 15.2 検出アーキテクチャ

```
forward_audio()                          Fingerprint Thread
     │                                        │
     ├─ メンバーに転送 (変更なし)               │
     ├─ フィンガープリントバッファをtry_lock     │
     │   ├─ 成功: 480サンプルをコピー           │
     │   └─ 失敗: スキップ (待機なし)           │
     │                                        │
     │                              5秒ごと:
     │                              ├─ リングバッファから5秒分のオーディオを読み取り
     │                              ├─ スペクトルフィンガープリントを計算
     │                              ├─ データベースと照合
     │                              └─ 一致 → COPYRIGHT_DETECT
```

フィンガープリントバッファはロックフリーリング（try_lock、ブロッキングなし）。フィンガープリントスレッドがロックを保持している場合、オーディオパケットは単純にスキップされる — これは5秒に最大1回発生するのみで、転送遅延への影響はゼロ。

### 15.3 プロトコルコマンド

#### リレー → DJ

```
← COPYRIGHT_DETECT:<json>\n
    {
      "track": "Song Title",
      "artist": "Artist Name",
      "album": "Album Name",
      "isrc": "US-XXX-YY-NNNNN",
      "rights_holder": "Record Label Inc.",
      "confidence": 0.95,
      "action": "warn",
      "royalty_per_listener": "0.003"
    }

    著作権のある楽曲が検出された際に送信。
    action: "warn" (通知), "charge" (自動課金), "block" (再生停止)。

← COPYRIGHT_WARN:<message>\n
    人間が読める警告テキスト。

← COPYRIGHT_CHARGE:<amount_cents>:<currency>:<isrc>\n
    DJに課金。金額 = レート × リスナー数 × 再生時間。
```

#### DJ → リレー

```
→ COPYRIGHT_ACK\n
    DJが著作権検出を認知し、ロイヤリティ課金に同意。

→ COPYRIGHT_SKIP\n
    DJが課金を最小限にするため次の曲にスキップ。
```

#### リレー → 全メンバー

```
← COPYRIGHT_INFO:<json>\n
    {
      "track": "Song Title",
      "artist": "Artist Name",
      "album": "Album Name",
      "rights_holder": "Record Label Inc.",
      "now_playing": true
    }

    適切な帰属表示付きの「再生中」情報。
    全リスナーに表示。警告ではなく、クレジット表示のみ。
```

### 15.4 オーディオフィンガープリンティング

フィンガープリントアルゴリズム:

1. **ダウンサンプル**: ステレオ S24 (48kHz) → モノ S16 (48kHz)、L+Rを平均化してトランケート
2. **ウィンドウ**: 5秒間のオーディオ (240,000サンプル)
3. **スペクトル解析**: 32ウィンドウに分割し、8つの周波数帯域（200Hz〜25.6kHz）のエネルギーを計算
4. **ハッシュ**: 各ウィンドウについて、前のウィンドウとの帯域エネルギーを比較 → 増加で1ビット → 64ビットフィンガープリントハッシュ

これはChromaprintの簡略版である。本番環境での精度向上には、外部APIを使用するようリレーを設定できる:

```
--fingerprint-api https://api.acrcloud.com/v1/identify
--fingerprint-api-key <KEY>
```

外部APIは1億曲以上のカタログに対して95%以上の精度を提供する。

### 15.5 ロイヤリティ計算

ロイヤリティは**ボリュームディスカウント付きのリスナーあたり・分あたりの段階制料金**を使用する（完全なレート表は§16.8を参照）。

```
charge_per_minute = calculate_royalty_per_min(listener_count)

段階制レート:
  1〜100リスナー:        $0.001 / 人 / 分
  101〜1,000:            $0.0005
  1,001〜10,000:         $0.0002
  10,001〜100,000:       $0.0001
  100,001+:              $0.00005
```

例（1分あたり）:
| リスナー数 | レート/分 | 4分の楽曲 |
|-----------|----------|------------|
| 10 | $0.010 | $0.040 |
| 1,000 | $0.550 | $2.200 |
| 100,000 | $6.000 | $24.000 |
| 1,000,000 | $56.000 | $224.000 |

10秒未満の再生はカウントされない（スキップ/プレビュー）。

### 15.6 ロイヤリティ台帳

すべてのロイヤリティイベントはJSONLファイル (`/data/royalties.jsonl`) に記録される:

```json
{"ts":1741737600,"group":"channel-name","dj":"DJ-Device","isrc":"US-XXX-YY-NNNNN","track":"Song Title","artist":"Artist","rights_holder":"Label Inc","duration_sec":240,"listeners":1500,"royalty_usd":13.5000}
```

この台帳は以下の情報源となる:
- 権利者への月次ロイヤリティレポート
- DJへの請求書発行
- 規制遵守（複製権ライセンス、演奏権）

### 15.7 収益分配

```
┌────────────────────────────────────────┐
│  1再生あたりのロイヤリティ収入           │
│                                        │
│  70% → 権利者 (アーティスト/レーベル)   │
│  10% → プラットフォーム (Soluna)        │
│  20% → DJ (適正利用へのインセンティブ)   │
└────────────────────────────────────────┘
```

70/10/20の分配はDJへの還元を最大化しつつ、業界標準の権利者シェアを維持している。

### 15.8 エンフォースメントレベル

チャンネルごとに設定可能:

| レベル | 動作 |
|-------|----------|
| `monitor` | 検出と記録のみ。警告なし。無料チャンネルのデフォルト。 |
| `warn` | DJにCOPYRIGHT_DETECTを送信。ロイヤリティを記録。 |
| `charge` | DJのアカウントから自動課金。COPYRIGHT_ACKまたはスキップを要求。 |
| `block` | DJが30秒以内に確認しなければオーディオ転送を停止。 |

### 15.9 FILE_URL (§14) との統合

DJが `FILE_URL` で楽曲を配信する場合:
- URL自体が楽曲を特定できる（例: Spotify/Apple Musicリンク）
- オーディオフィンガープリンティング不要 — メタデータは既知
- ロイヤリティ追跡は即時かつ100%正確

これが推奨パスである: `FILE_URL` は即時検出 + 適切なクレジット表示を提供する。

### 15.10 プライバシー

- フィンガープリントは一方向ハッシュ — 元のオーディオは復元不可
- 権利者と共有されるのは集計された再生数とロイヤリティ合計のみ
- 個々のリスナーの身元は公開されない
- DJは自身のロイヤリティ課金をリアルタイムで確認可能

## 16. 課金、ウォレット、ロイヤリティ支払い

OSTPには、音楽権利者への公正な報酬のための経済レイヤーが組み込まれている。

### 16.1 ビジネスモデル

```
┌──────────────────────────────────────────────────────────┐
│  DJ (ブロードキャスター) → ウォレットに事前チャージ → 楽曲再生 │
│    ├─ パブリックチャンネル + 著作権楽曲 → ロイヤリティ課金    │
│    │    ├─ 70% → 権利者 (アーティスト/レーベル)             │
│    │    ├─ 20% → プラットフォーム (Soluna)                  │
│    │    └─ 10% → DJキャッシュバック                         │
│    ├─ プライベートチャンネル → 課金なし (著作権チェックなし)  │
│    └─ LAN / P2P直接 → 課金なし (リレー不使用)              │
│                                                          │
│  リスナー → 常に無料 (広告なし、サブスクリプションなし)       │
│                                                          │
│  チップ → 100% DJ (リスナーが任意で送金)                    │
└──────────────────────────────────────────────────────────┘
```

### 16.2 DJが支払う理由（リスナーではなく）

| モデル | 問題点 |
|-------|---------|
| リスナーサブスクリプション | 成長を阻害する。オーディオは無料であるべき。 |
| 広告 | オーディオ品質を損なう。Solunaの理念に反する。 |
| DJ定額制 | 小規模DJに不公平。大規模チャンネルが小規模を補助する形に。 |
| **DJ従量制** | **公平。利用量に比例。リスナーは無料。** |

オリジナル/CCライセンス楽曲を再生するDJや、プライベートモードを使用するDJは支払い不要。

### 16.3 ウォレットプロトコル

#### 残高照会

```
→ WALLET\n
← WALLET:{"balance":12.50,"total_charged":100.00,"total_earned":5.00,"total_royalties":82.50}\n
```

#### 入金

```
→ CHARGE:<amount_usd>:<payment_token>\n
← OK:charged:{"balance":112.50,"amount":100.00}\n
← ERR:payment_failed\n
```

`payment_token` は決済ゲートウェイ（Stripe等）からの参照。リレーはWebhookで検証後に入金処理する。

#### 出金

```
→ WITHDRAW:<amount_usd>\n
← OK:withdrawn:{"amount":50.00,"remaining":62.50}\n
← ERR:insufficient_balance\n
← ERR:no_payout_account\n
```

DJ（キャッシュバック収入、チップ）および権利者（ロイヤリティ収入）が利用可能。出金は登録済みの支払い先アカウントに処理される。

#### 支払い先アカウント設定

```
→ PAYOUT_SETUP:<stripe|paypal>:<account_id>\n
← OK:payout_setup\n
```

#### チップ

```
→ TIP:<amount_usd>\n
← OK:tipped:{"amount":1.00,"to":"DJ-Device"}\n
    DJが受信: TIP_RECEIVED:{"amount":1.00,"from":"Listener-Device"}\n
← ERR:insufficient_balance\n
```

チップは100%DJへ。プラットフォーム手数料なし。チップを送るにはウォレットに残高が必要。

#### サポート（DJのロイヤリティコスト支援）

```
→ SUPPORT:<amount_usd>\n
← OK:supported:{"amount":5.00,"to":"DJ-Device","balance":45.00}\n
    全メンバーが受信: SUPPORT_RECEIVED:{"amount":5.00,"from":"Supporter","dj":"DJ","dj_balance":50.00}\n
← ERR:insufficient_balance\n
```

リスナーがDJのウォレットに直接入金し、ロイヤリティコストをカバーする。チップ（プライベート）とは異なり、SUPPORTは全メンバーにブロードキャストされる — 音楽を続けるために誰が支援しているか全員が確認できる。

#### DJ残高ブロードキャスト

```
← BALANCE_UPDATE:{"dj":"DJ-Device","balance":12.50,"rate_per_min":0.15,"listeners":50,"track":"Song","artist":"Artist"}\n
```

著作権楽曲の再生中、60秒ごとに全メンバーに送信。リスナーはDJの残高がリアルタイムで減少していくのを確認でき、SUPPORT投稿を促す。

#### ライセンス済み再生（ワンクリック、検出なし）

```
→ LICENSED_PLAY:{"track":"Song","artist":"Artist","isrc":"XX-XXX-YY-NNNNN","license":"jasrac"}\n
← OK:licensed_play\n
    全メンバーが受信: COPYRIGHT_INFO:{"track":"Song","artist":"Artist",...}\n
```

DJが有効なライセンス（JASRAC、CC、ブランケット、オリジナル）を保有していることを宣言。この楽曲の著作権検出は抑制される。監査用に記録されるがロイヤリティ課金なし。ライセンス済みコンテンツのワンクリック再生を可能にする。

#### 取引履歴

```
→ TRANSACTIONS:<count>\n
← TRANSACTIONS:[{"ts":1741737600,"type":"royalty","amount":0.45,"track":"Song","balance":12.05},...]
```

### 16.4 リアルタイムロイヤリティ課金

ロイヤリティは楽曲終了時ではなく、リアルタイムで差し引かれる:

1. 著作権検出が楽曲を特定（§15）
2. 再生中60秒ごとに、リレーが段階制料金で計算:
   ```
   charge = calculate_royalty_per_min(listener_count) × 1 minute
   ```
3. DJのウォレットから引き落とし。権利者、プラットフォーム、DJキャッシュバックに入金
4. DJに `COPYRIGHT_CHARGE` が送信され、金額と残高が通知される
5. 楽曲終了時に最後の端数分が精算される

これにより権利者はリアルタイムで収益を確認できる。

### 16.5 残高不足時の処理

| DJ残高 | 動作 |
|-----------|----------|
| > $1.00 | 通常動作、定期的な課金 |
| $0.01〜$1.00 | 残高低下の `COPYRIGHT_WARN` アラート |
| $0.00 | 警告付き5分間の猶予期間 |
| $0.00 + 5分 | 自動的にプライベートモードへ切り替え (`MODE:private`) |

DJは入金（`CHARGE`）によりパブリックモードに復帰できる。音楽は決して停止しない — チャンネルモードのみが変更される。

### 16.6 権利者ダッシュボード

権利者はISRCトラックごとの収益を蓄積する:

```
→ RIGHTS_BALANCE:<isrc_or_name>\n
← RIGHTS_BALANCE:{"rights_holder":"Label Inc","pending":1250.00,"total_earned":15000.00,"tracks":[...]}\n
```

登録済みの支払い先アカウントへの出金はいつでも `WITHDRAW` で可能。

> **注**: `RIGHTS_BALANCE` は将来のリリースで実装予定。現在、権利者の収益はロイヤリティ台帳 (`/data/royalties.jsonl`) で追跡され、オフラインで照会可能。

### 16.7 トランザクション台帳

すべての金融イベントは `/data/transactions.jsonl` に記録される:

```json
{"ts":1741737600,"tx_id":"tx_abc123","from":"DJ-Device","to":"rights:US-XXX-YY-NNNNN","amount":0.45,"type":"royalty","desc":"Song Title by Artist"}
{"ts":1741737600,"tx_id":"tx_abc124","from":"DJ-Device","to":"platform","amount":0.13,"type":"platform_fee","desc":"20% platform fee"}
{"ts":1741737600,"tx_id":"tx_abc125","from":"platform","to":"DJ-Device","amount":0.06,"type":"cashback","desc":"10% DJ cashback"}
{"ts":1741737660,"tx_id":"tx_abc126","from":"Listener1","to":"DJ-Device","amount":1.00,"type":"tip","desc":"Tip"}
```

この台帳の特徴:
- **追記専用** — 書き込み後の変更なし
- **リアルタイム** — すべての金融イベントで書き込み
- **監査可能** — 規制遵守のための完全な履歴

### 16.8 段階制料金

### 16.9 無料シナリオ（課金なし）

- **プライベートモード** → 著作権検出なし → 課金なし
- **LANマルチキャスト** → リレーなし → 課金なし
- **P2P直接** → リレーなし → 課金なし
- **オリジナル/CC楽曲** → 著作権一致なし → 課金なし
- **ライセンス済みコンテンツのFILE_URL** → ロイヤリティはURLソース（Spotify等）で処理
